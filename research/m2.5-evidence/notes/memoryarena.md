## 1. What the paper says (thin, from A, S4, D)

A (verbatim abstract):
> "Existing evaluations of agents with memory typically assess memorization and action in isolation. ... we introduce MemoryArena, a unified evaluation gym for benchmarking agent memory in multi-session Memory-Agent-Environment loops. The benchmark consists of human-crafted agentic tasks with explicitly interdependent subtasks, where agents must learn from earlier actions and feedback by distilling experiences into memory, and subsequently use that memory to guide later actions to solve the overall task. MemoryArena supports evaluation across web navigation, preference-constrained planning, progressive information search, and sequential formal reasoning, and reveals that agents with near-saturated performance on existing long-context memory benchmarks like LoCoMo perform poorly in our agentic setting"

Authors (A): Zexue He, Yu Wang, Churan Zhi, Yuanzhe Hu, Tzu-Ping Chen, Lang Yin, Ze Chen, Tong Arthur Wu, Siru Ouyang,
Zihan Wang, Jiaxin Pei, Julian McAuley, Yejin Choi, Alex Pentland.

S4 (search extract of arxiv.org/html/2602.16313v1):
> "MemoryArena is instantiated across four domains: (1) bundled web shopping, (2) preference-constrained group travel planning, (3) progressive information searching, and (4) sequential formal reasoning over math and physical problems."
> "Each task spans long horizons (with an average of 57 action steps) and produces extended reasoning traces with more than 40k tokens."

D (LOW confidence, LLM digest):
> "The benchmark comprises 766 human-curated tasks across four environments."
> "at the start of each subtask they retrieve relevant memories from a store M; they then interact with the environment until the subtask completes; finally, they update M with the trajectory."
> "The primary metrics are Success Rate (SR), Progress Score (PS), SR@k (success after k subtasks to measure decay), and subtask latency."
> "External memory and RAG do not universally beat simple long-context agents; they only improve results in domains with exceptionally long traces (Progressive Web Search, Formal Reasoning) but incur higher latency."

L (third party): "across all five MemoryArena domains". In the repo, math and physics are separate HF configs, so four
paper domains map to five evaluated sets. L also says: "A separate MemoryLake-only run over all 221 progressive queries".

I could not verify the "ICML 2026" venue from the task prompt. The README BibTeX (README.md:32-37) cites it as
"arXiv preprint arXiv:2602.16313".

## 2. Repository structure and interfaces (verified, R)

README.md:13-27:
> "- `agent/`: task agent implementations.
> - `env/`: environment server, client, and environment systems.
> - `memory/`: memory client and memory systems including long-context, letta, mirix, mem0, mem0-g, ReasoningBank, BM25, Text-embedding RAG,  GraphRAG,  and MemoRAG."
> "1. Task prompt → memory wraps prompt 2. Agent generates action 3. Env `step()` executes tool or accepts final 4. Observation + reward returned 5. Memory stores action/observation/reward(optional)"
README.md:7: "*This code is preview version. We are still actively maintaining and improving this codebase.*"

### 2.1 Memory interface (the main plug-in point)

`memory/server.py` is a FastAPI server with three endpoints: `/memory/initialize`, `/memory/add` and
`/memory/wrap_user_prompt` (server.py:86-119). Each memory system must implement exactly two methods:
- `memory/server.py:109`: `response = memory_system.add_chunk(req.chunk)`
- `memory/server.py:118`: `prompt = memory_system.wrap_user_prompt(req.question)`

The registry is `memory/server.py:49-62`:
```
MEMORY_FACTORIES = {
    "mirix": MirixMemorySystem,
    "long_context": LongContextMemorySystem,
    "mem0": Mem0MemorySystem,
    "mem0-g": lambda: Mem0MemorySystem(enable_graph=True),
    "letta": LettaMemorySystem,
    "rag": RAGMemorySystem,
    "memorag": MemoRAGMemorySystem,
    "graphrag": GraphRAGMemorySystem,
    "amem": AMemMemorySystem,
    "lightmem": LightMemMemorySystem,
    "reasoningbank": ReasoningBankMemorySystem, ...
    "zep": ZepMemorySystem,
}
```
`server.py:89-90` special-cases `bm25` and `text-embedding-3-small`, building `RAGMemorySystem(retrieval_method=name)`.
`memory_systems/__init__.py:7`: `from .langchain_graphrag import GraphRAGMemorySystem`. So "graphrag" means a
LangChain `GraphRetriever` over an `InMemoryVectorStore` (langchain_graphrag.py:86-100) with edges
`[("user_id","user_id")]` (line 23). It is **not** Microsoft GraphRAG: `graphrag.py` (the CLI-based MS GraphRAG
wrapper) is commented out at server.py:91-94.

The client is `memory/client.py:5-50` (`MemoryClient(user_id, memory_system_name, base_url)` with `.add(chunk)` and
`.wrap_user_prompt(question)`). Memory instances live in a process-local dict, `MEMORY_SYSTEMS` (server.py:74), so
they are not persisted across server restarts.

`memory/README.md:34-46` shows how to adapt an external agent loop:
```
+ task_id = uuid.uuid4()
+ client = MemoryClient(task_id, memory_system_name='mirix')
 obs = get_initial_obs(env)
 for i in range(max_turns):
+    prompt = client.wrap_user_prompt(obs)
-    action = agent.query(obs, instruction)
+    action = agent.query(prompt, instruction)
     obs = env(action)
+    client.add(f"action: {action}\\nobs: {obs}")
```

**Implication.** A memory system is an opaque text-in/text-out box. It has no time argument, no delete/update, no
as-of query, and no structured state returned to the harness.

### 2.2 Memory systems: what each adapter does (verified)

Returns the whole context. Probe P confirmed that the oldest chunk is dropped once the budget is exceeded. |
| bm25 / text-embedding-3-small | rag.py:15-68 | Splits chunks into ≤2048-token pieces, appends them, retrieves `top_k=3`. P shows bm25 returns 1 doc with top_k=1. No delete/update methods (P lists the attributes). |

### 2.3 Agent interface

`agent/base.py:5-66` defines `BaseAgent(ABC)` with abstract `build_memory_entry(task, action, observation, reward) -> str`
and `act(prompt) -> str`. Docstring (base.py:60): "memory_context: memory context extracted from the memory
system. (Your memory system should have all history with previous task, actions/trajectories, and observations.)"
In practice each domain has its own agent (`WebShopAgent`, `TravelPlannerAgent`, `MathAgent`) and its own runner
(`run_shopping.py`, `run_travel.py`, `run_math.py`, `run_search.py`). The search agent runs as a **subprocess
script** (`script_path`, default `web_search_env/search_agent/openai_client.py`; run_search.py:278-282). **Adapting an
external agent therefore means replacing or editing the per-domain runner or agent; there is no single agent API.**

### 2.4 Environment interface

`env/env_systems/base_env.py:5-42` defines `BaseEnvironment` with `reset(seed)`, `step(action, ground_truth=None,
need_judge=False)`, `get_observation()` and `close()`. `env/env_server.py:52-61` holds the registry `ENV_FACTORIES`:
webshop, browsecomp-plus, travel_planner, math, phys ("formal reasoning environment is shared between math and
phys"). Note env_server.py:125-143: **the runner passes ground truth into env.step** (`ground_truth=req.ground_truth`)
for judging. `env/README.md` tells you how to add an env.

## 3. Task structure per domain (verified in code; counts mostly unverifiable)

### 3.1 Bundled web shopping
- Data: HF `ZexueHe/memoryarena` config `bundled_shopping`, split `test` (`runtime/runner/task_files.py:12-14`). Note
  that setup_web_shopping.md:7 says config `web_shopping`, which disagrees with the code.
- Row schema, task_files.py:21-26: "`id` ... `questions` – list of per-step agent instructions (one per product) ...
  `answers` – list of `{target_asin, attributes}` dicts ... `category` – string like `"baking_item_0"`".
  Categories (docstring example, task_files.py:160): `["baking", "beauty", "electronics", "grocery", "home_decor", "mens_outfit"]`.
- Multi-session structure: in `split_steps=True` mode (the default), **each product is a separate episode with a fresh
  env instance** (`run_episode` creates `EnvironmentClient(task_id=str(uuid.uuid4()))`, run_shopping.py:887, 908-915).
  One memory instance persists across a task's steps: `task_memory_user_id` →
  `f"shopping::{task_key}::{args.model_name}::{args.memory_system}"` (run_shopping.py:443-445).
- Memory is read **only on the first turn of each step**: run_shopping.py:919-921
  `if memory is not None and not memory_injected: prompt = memory.wrap_user_prompt(prompt_source); memory_injected = True`.
- Memory write: per turn (`use_step_memory`) or at episode end (run_shopping.py:977-980, 1010-1015). Entry format
  (run_shopping.py:807-820): `"Step {i}:\nUser Instruction: ...\nAgent Action: ...\nEnv Observation: ...\nDone: ..."`.
- Instruction for step k (task_files.py:206-251): prefix plus the current product only. With `include_history=True`,
  earlier sections are replaced by feedback, and the reminder reads (task_files.py:240-243): "You only need to buy the
  item for this step; use the ground-truth items in Purchase History as references and follow the requirements to buy
  the correct item." The feedback string (summary_build.py:72-75):
  `f"Product {step_num} shopping result: bought {asin_text} ({name_text}) at {price_text}; {match_text} (ground truth: {target_asin} ({target_name_text}))."`
  **Default `include_history` is False** (run_shopping.py:293; all shipped shopping configs set `"include_history": false`).
- Optional in-env feedback `enable_feedback` (default false in configs) appends, after each purchase,
  `"The answer is {verdict} because the Ground Truth answer is: {ground_truth}"` (webshop_plus_client.py:996-999; f-string at :998).
- Scoring: `match_ground_truth` = exact ASIN match (webshop_env.py:267-277); `overall_success = total_steps > 0 and
  matched_steps == total_steps` (run_shopping.py:1046). `compute_reward.py:5-10` gives a soft reward:
  "reward = r_type * (r_attr + r_price) / (# terms with constraints) ... reward = 1.0 if purchased ASIN == target ASIN",
  with attribute matching judged by an LLM (default gpt-4o per setup_web_shopping.md:190).
- No action can undo or return a purchase. Grep for refund/cancel/undo/revis*/invalidat* finds nothing relevant in the
  agent, env or runner code.

### 3.2 Group travel planning
- Data: HF config `group_travel_planner` (travel_planner_env/data_loader.py:4-5). setup_travel.md:7 says "**Dataset**:
  270 groups". Each row has `base_person` (with a fixed plan), `questions` (one per later traveler) and `answers`
  (per-traveler GT daily plans) (data_loader.py:13-40).
- Tools: FlightSearch, RestaurantSearch, AccommodationSearch, AttractionSearch, DistanceMatrix, CitySearch over local
  CSVs (setup_travel.md:8). These are static databases; no world state changes.
- Loop (run_travel.py:245-356): for each traveler, wrap the query with memory, run a ReAct tool loop
  (agent/travel_planner.py:154-268), call env.step with GT for judging, then
  `memory_system.add(agent.build_memory_entry(...))`. The memory entry is JSON with name, query, scratchpad,
  final_plan and optional judgement (travel_planner.py:270-292).
- With memory_system "none", the agent gets the previous plans and judgement in-context instead:
  `include_previous_plans=(memory_system is None)` (run_travel.py:275). So the "none" baseline still sees prior plans
  in context.
- `judgement_mode`: `none` | `hint` (lists slots needing correction) | `answer` (reveals the GT plan)
  (travel_env.py:60-92, 160-163). Shipped configs use `"judgement_mode": "none"`.
- **Revision affordance (important for this project).** `travel_planner_env/prompts.py:12-18` (`SYSTEM_PROMPT`):
  "You may adjust previous travelers' plans if needed to accommodate new constraints, but the first traveler's plan is
  FIXED and cannot be changed ... Turn 2 (Traveler C joins): Output B's AND C's plans (you may adjust B's plan if
  needed)". **This `SYSTEM_PROMPT` is never imported.** The agent imports only `AGENT_SYSTEM_PROMPT`,
  `AGENT_USER_PROMPT_TEMPLATE`, `HISTORY_TEMPLATE` and `BASE_PERSON_TEMPLATE` (agent/travel_planner.py:11-16), and the
  active user prompt says "Create a travel plan for {name}" (prompts.py:132). Mechanically, `parse_all_plans`
  (run_travel.py:39-63) builds `name_plan_pairs[name] = plan` (line 49) over the accumulated outputs, so a later re-output of an
  earlier traveler's plan would overwrite the earlier one for scoring. The GT for each traveler is fixed, though
  (eval.py:21-38).
- Metrics (travel_planner_env/eval.py:112-205): **SR** = groups where every person fully passes; **PS** = persons fully
  passing; **SPS** = per-group average pass rate over "constraint slots", defined as slots where the person's GT
  differs from the base person's GT (`find_constraint_slots`, eval.py:66-83). Slot match uses SequenceMatcher ratio
  ≥ 0.7.

### 3.3 Formal reasoning (math, physics)
- Data: HF configs `formal_reasoning_math` / `formal_reasoning_phys`. Row keys (run_math.py:246-249) are
  `['id', 'paper_name', 'questions', 'answers', 'backgrounds']`. Each "paper" is a task whose questions are sequential
  subtasks.
- Loop (run_math.py:155-200): for each subtask, `prompt = memory_client.wrap_user_prompt(query)`; act; env.step with
  GT and an LLM judge (math_env.py `judge`: "Determine if these two expressions are mathematically equivalent");
  add a memory entry. By default the judge result is **not** put in memory (run_math.py:168-198, `reward=None`).
  setup_formal_reasoning.md:102: "the judge result won't be added into memory".
- Metrics (formal_reasoning_env/eval.py:40-73): `progress_score = correct_count / length`; `is_paper_correct` = last
  subtask correct (`if logs[-1].get('is_correct', True)`); plus passrate@k and cumulative passrate@k.

### 3.4 Progressive web search (BrowseComp-Plus)
- Data: BrowseComp-Plus (`Tevatron/browsecomp-plus`, setup_web_search_env.md:3). Subqueries and answers come from
  `browsecomp_all_jsons.jsonl` on HF `joanna690/websearch-embeddings` (setup_web_search_env.md:229-241).
- Loop: `env.step({"command": "run_sequential"})` (run_search.py:340). The **env server** runs each subquery with the
  agent, writes `f"Subquery {i + 1}: {subquery}\n\nPredicted Answer: {answer}"` plus the trace to memory
  (browsecomp_plus_env.py:189-222), then runs the original full query with memory (`final_query = original_query`,
  line 282) and judges it.
- Metrics (run_search.py:385-430): accuracy (LLM judge, gpt-4.1), evidence recall, calibration error
  `abs(confidence / 100.0 - acc_val)` (run_search.py:186-190), using the agent's self-reported "Confidence: ..."
  (search_agent/prompts.py:9).
- `store_eval_in_memory` is plumbed into `run_final_query` (browsecomp_plus_env.py:245, 270) but I found no use of it
  in that function body (lines 271-381).

## 4. What memory must do (code-level synthesis)

In every domain, the harness writes one text record per turn, subtask or traveler into a per-task memory instance. At
the start of the next subtask it calls `wrap_user_prompt(current subtask text)` and prepends the returned
`<memory_context>...</memory_context>`. Memory must surface the earlier facts the current subtask depends on (the
earlier purchase, earlier travelers' plans, earlier lemmas or results, earlier subquery answers). Dependencies run
forward: later subtasks consume earlier outcomes. The harness does not ask memory to retract, version or
time-index anything. Memory is per task (user_id per task or group or paper), so there is no cross-task learning
except inside ReasoningBank's per-user_id store.

## 5. Revisiting earlier decisions: does any task require it?

**Verified in code: no implemented task requires noticing that later information invalidates an earlier decision and
then revisiting that decision.**
- Shopping: each purchase is terminal within its own episode, there is no undo action, and each step is scored once.
  When feedback is enabled, the harness itself *tells* the agent the ground-truth item. It does not test whether the
  agent notices the mistake. Later steps are told to use the ground-truth items as references (only when
  `include_history=True`).
- Travel: the only revision language (`SYSTEM_PROMPT`, prompts.py:12-18) is dead code. The active prompt asks only
  for the new traveler's plan. The scorer would accept a revised earlier plan, because the dict overwrite at
  run_travel.py:49 keeps the last occurrence. Each traveler's GT is fixed in the dataset. I could not inspect the
  data to check whether any later traveler's query makes an earlier traveler's GT depend on information unavailable
  at that earlier round.
- Math/physics: each subtask is judged when answered. An earlier wrong answer is never re-scored. Correctness
  feedback stays out of memory unless `judge_result_in_memory=True`.
- Search: subquery answers are not re-scored; only the final combined query is. D describes the domain as
  "accumulating constraints", but I could not verify from data whether later subqueries contradict earlier
  candidates.

## 7. Reproducibility and quality observations (verified)

- Only one commit, labelled "preview version" (README.md:7).
- Docs and code disagree:
  - Default env-server port: `uvicorn.run(app, host="0.0.0.0", port=8001)` at env_server.py:232, but
    setup_web_shopping.md:146 and setup_travel.md:113 say 8005.
  - The shopping HF config is named `web_shopping` in the doc but `bundled_shopping` in the code.
  - `configs/web_shopping_configs/all_systems_reference.json` (setup_web_shopping.md:114) and `shopping_task.json`
    (DEFAULT_CONFIG, run_shopping.py:48) are missing.
  - setup_web_search_env.md:144-150 says "cd env/MemActBench; python server.py", but that directory is a missing
    submodule.
  - setup_travel.md:109 says the memory server is not needed for long_context, but run_travel.py:26-30 sends
    long_context through `MemoryClient` as well.
- Non-determinism: shopping configs use `"temperature": 1.0` (bm25.json). The judges are LLMs (math equivalence,
  shopping attributes, search grading). The memory backends are cloud services (Mem0, Letta, MIRIX, Zep).
- Ground-truth exposure inside runner processes:
  - travel `env.reset` returns `"answers"` to the runner (travel_env.py:127; run_travel.py:201);
  - the shopping observation dict carries `"target_products"` (webshop_env.py:286), but only `observation["state"]`
    reaches the agent prompt (run_shopping.py:918);
  - the math runner holds `ground_truth` (run_math.py:154).
  An externally adapted agent placed in the runner would need care to avoid leakage.
- Resume:
  - shopping resumes at the first incomplete step. It rebuilds memory by **re-adding** stored `memory_entries` to a
    fresh memory instance (`backfill_memory_from_artifacts`, run_shopping.py:823-856; called at 1091-1092). With
    long_context, the re-added chunks get **new wall-clock stamps** (long_context.py:20), so original timing is lost.
  - travel and math skip completed groups or papers only (run_travel.py:186-188; run_math.py:62-80, 104-109).
- Traces:
  - shopping writes `interaction_history/eval_{stem}_step_{n}_{timestamp}.json` with per-turn `input_messages`, which
    include the memory-wrapped prompt (run_shopping.py:859-875, 689-711), plus `step_results/*_results_{timestamp}.json`;
  - math logs per-subtask `memory_context`, response and GT (run_math.py:206-216);
  - search saves `final_query_memory_context.json` (browsecomp_plus_env.py:328-341).
